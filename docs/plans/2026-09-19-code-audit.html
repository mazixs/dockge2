2. Дефекты, ломающие пользовательский сценарий

P0-1 Отказ терминала не доходит до браузера, интерфейс остается заблокированным

backend/terminal.ts:375 → backend/util-server.ts:52 → frontend/src/pages/Compose.vue:838

Суть
Когда имя терминала занято, Terminal.exec делает reject("Another operation is already running, please try again later.") - отклоняет строкой, а не объектом Error. Функция callbackError разбирает только ValidationError и Error; для всего остального она пишет log.debug("console", "Unknown error: " + error) и не вызывает callback вообще.
Следствие
Браузер ждет ack, который никогда не придет. В Compose.vue метод deployStack ставит processing = true и снимает флаг только в колбэке, поэтому кнопки стека остаются неактивными до перезагрузки страницы. Пользователь не видит ни ошибки, ни причины.
Нюансы
Перед вызовом Compose.vue посылает run-start, а run-end шлет только из колбэка, поэтому в StackInspector.vue:298 часы прогресса тоже не останавливаются. Одна вкладка воспроизвести это не может: кнопки заблокированы флагом processing. Воспроизводится второй вкладкой или вторым пользователем на том же стеке. Тот же путь у start, stop, restart, update и delete - все они идут через Terminal.exec.
Статус
Проверено запуском: пробный вызов callbackError со строкой дал "callback вызван: false".
Правка
Два независимых исправления: (1) в terminal.ts отклонять через new Error(...) с ключом перевода; (2) в callbackError добавить ветку по умолчанию, которая всегда отвечает клиенту общим сообщением и логирует исходное значение на уровне error, а не debug. Вторая правка закрывает весь класс подобных мест сразу.
Проверка
Юнит-тест callbackError со строкой, числом и undefined; тест Terminal.exec при занятом имени; ручной прогон развертывания с параллельной операцией.

P0-2 Серверные сообщения помечены как переводимые, но ключей перевода не имеют

backend/util-server.ts:58-70 → frontend/src/main.ts:82-88

Суть
callbackError в обеих ветках ставит msgi18n: true. Фронт в translateServerMessage проверяет $te(key) и, не найдя ключ, показывает $t("unexpectedServerError", { detail: key }), то есть "Unexpected error:" плюс сырой текст. В обработчиках backend/socket-handlers и backend/agent-socket-handlers из 19 уникальных текстов ошибок ключами являются только два: authInvalidUserData и authAccountExists. Успешных ответов это не касается: все их сообщения (Deployed, Saved, Stopped и остальные) в каталоге есть.
Следствие
Пользователь в подавляющем большинстве отказов видит "Unexpected error: Terminal name must be a string." вместо человеческого сообщения на своем языке. Ошибка выглядит как сбой панели, а не как отказ операции.
Правка
Завести ключи в en.json и ru.json для сообщений, которые видит пользователь; остальные (нарушение контракта, а не пользовательская ситуация) отдавать с msgi18n: false и общим текстом. Ставить msgi18n: true только там, где ключ действительно существует.
Проверка
Тест, который проходит по всем вызовам callbackError в обработчиках и требует, чтобы сообщение с msgi18n: true имелось в en.json. Это дешевле разовой чистки и не дает проблеме вернуться.

P0-3 Русские строки интерфейса приходят с сервера

backend/agent-socket-handlers/git-socket-handler.ts:26,44,58,71,89,103,119,132,148, весь backend/stack-git.ts

Суть
Git-поток отдает клиенту готовые русские предложения: "Укажите адрес репозитория.", "Выбранный результат не прошел проверку Compose...", "Файлы сохранены, но развертывание не завершено...". Все сообщения StackGitError в stack-git.ts тоже на русском. Все 43 строковых литерала с кириллицей в backend лежат в этих двух файлах; еще в семи файлах кириллица есть только в комментариях.
Следствие
Нарушено правило проекта из AGENTS.md: продукт ведется на английском, остальные языки переводятся с него. Практически: англоязычный пользователь в главном сценарии продукта (Git-поток) получает русский текст, и перевести его нечем - строки не проходят через каталоги.
Правка
Перевести на английский и одновременно с P0-2 перевести на ключи. Работы немного, поскольку это тот же набор сообщений, но делать надо одним изменением, иначе придется трогать файлы дважды.

P0-4 Причина отказа Compose теряется полностью

backend/agent-socket-handlers/git-socket-handler.ts:43-45 и :70-72

Суть
Функция validate оборачивает весь блок в catch { throw new StackGitError(...) }. Исходная ошибка не логируется и не сохраняется нигде. То же в result: неуспешное развертывание превращается в общий текст без записи причины.
Следствие
Пользователю говорят "не прошел проверку Compose", а в журнале сервера пусто. Диагностировать нечем ни ему, ни поддержке. Это единственная точка, где могла бы быть видна реальная ошибка docker compose config.
Правка
Логировать причину на сервере (log.warn с именем стека), клиенту оставить общий текст. Решение не показывать вывод docker клиенту верное и его надо сохранить: вывод может содержать учетные данные из URL репозитория.

3. Производительность и корректность

P1-1 Docker опрашивается вдвое чаще, чем нужно

backend/dockge-server.ts:524-534, :731, :754; backend/stack.ts:559-630

Суть
Крон на 10 секунд вызывает подряд observeStacks() и sendStackList(true). Каждый из них независимо вызывает Stack.getStackList. Кеш managedStackList экономит только чтение каталога стеков: docker compose ls --all и getInstanceMap() (то есть docker ps) выполняются при любом значении флага кеша.
Следствие
Четыре вызова docker за тик вместо двух: 8 640 тиков в сутки, то есть около 17 280 лишних запусков процессов. На хосте с большим числом контейнеров это заметная фоновая нагрузка, которой никто не просил.
Правка
Получить список один раз в теле крона и передать его обоим потребителям. Сигнатуры observeStacks и sendStackList принимают уже готовую карту.
Проверка
Тест с подменой spawn, считающий вызовы docker на один тик.

P1-2 Кеш проверки обновлений образов растет без ограничения

backend/image-updates.ts:47, :175

Суть
const cache = new Map<string, CacheEntry>() не имеет ни предела размера, ни выселения по времени. Функция clearImageUpdateCache() не вызывается нигде, кроме тестов.
Следствие
Запись на каждый когда-либо встреченный тег образа живет до перезапуска процесса. Панель работает месяцами, поэтому утечка медленная, но безусловная.
Правка
Выселение по времени жизни записи плюс жесткий предел числа записей. Тест на вытеснение.

P1-3 Запись наблюдений на каждом тике

backend/observations.ts, backend/stability.ts

Суть
recordStatus на каждом тике выполняет UPDATE observed_until для каждого стека, и это по замыслу: availability считается только по подтвержденным интервалам, поэтому интервал надо продлевать каждым наблюдением. INSERT происходит только при смене статуса или после разрыва наблюдений.
Следствие
Один UPDATE на стек каждые 10 секунд плюс fillAvailability читает историю каждого стека на каждом тике для рассылки списка. При десятках стеков это постоянная фоновая работа SQLite, но не дефект.
Правка
Не требуется. Если появится измерение, что это заметно на реальной установке, продление интервала можно делать одним UPDATE по списку id, а не по одному на стек.

4. Технический долг

P2-1 Компоненты Vue не покрыты юнит-тестами

В test/frontend проверяются только чистые модули: каталоги переводов, множественные числа, токены оформления, форматирование, разметка статусов. Ни один из 51 компонента не имеет юнит-теста. Единственная страховка - 14 спеков Playwright и снимки, то есть самая медленная и хрупкая часть пирамиды. Логика в StackInspector.vue, Compose.vue и CreateStackSheet.vue проверяется только через браузер.

P2-2 Девять каталогов перевода заполнены на 14-17%

При 773 ключах в en.json и ru.json остальные языки содержат 111-130 ключей: de, es, fr, zh-CN по 130, ja 127, id 120, pt и ur по 114, ar 111. Интерфейс на этих языках наполовину английский. Вопрос "кто переводит" в мастер-плане открыт - см. раздел блокеров.

P2-3 RTL не сверстан, но языки RTL предлагаются

В frontend/src/i18n.ts массив rtlLangs пуст, при этом ar и ur присутствуют в списке языков. Арабский и урду отображаются слева направо. Либо верстка, либо временное изъятие языков из списка - промежуточного состояния быть не должно.

P2-4 Мертвый код и мертвые ключи

  • backend/database.ts: тип DBConfig.type допускает "mysql", хотя connect на нем бросает "Unknown Database type". Тип обещает то, чего нет.
  • getSize() и shrink() вызываются только из тестов.
  • Около 48 ключей en.json не встречаются в коде (подсчет сделан с исключением динамически собираемых префиксов вида serviceState_, gitUiFile_, mcpPermission_).
  • 96 ключей каталога записаны не в camelCase, вразрез с остальными.

P2-5 Комментарии на русском в коде, который ведется на английском

Кириллица в комментариях: 9 файлов backend и 138 строк во frontend (в основном комментарии в шаблонах Vue). Строк интерфейса среди них нет - на фронте это именно комментарии. В мастер-плане пункт уже стоит как осознанный и низкоприоритетный, поэтому здесь он зафиксирован, но в план правок вынесен последним.

P2-6 CI не проверяет два пути поставки

.github/workflows/ci.yml прогоняет lint, check-ts, test, сборку фронта, update-docker --dry-run, test:install, docker-integration и e2e. Не прогоняются: shellcheck по install.sh (это один из двух способов установить продукт) и визуальные тесты. Визуальные, вероятно, исключены намеренно из-за нестабильности снимков в CI, но shellcheck дешев и его отсутствие ничем не оправдано.

Это решение унаследовано от Dockge и работает, но означает: загрузчик в рантайме продакшн-образа, дополнительное время старта и отсутствие проверки, что артефакт сборки вообще собирается. Само по себе не дефект, но должно быть осознанным решением, а не умолчанием.

5. Блокеры исправлений

Блокер Нет чистого хоста для проверки на живом Docker

На машине разработки docker ps показывает чужие стеки, а правила проекта прямо запрещают их трогать при тестировании. Полноценно проверить P1-1 (частота опроса Docker), e2e и test:docker-integration в условиях, приближенных к продакшену, здесь нельзя. Нужен отдельный хост или изолированное окружение с DOCKGE_STACKS_DIR и своим набором стеков.

Блокер Мажорные обновления нельзя накатывать без полного прогона

typescript 7, express 5 и vue-router 5 меняют поведение. Для express 5 это маршруты и обработка ошибок, то есть напрямую монтирование /api/auth/* до парсеров тела запроса. Ручной прогон потока аутентификации обязателен, а он упирается в предыдущий блокер.

Блокер Переводы ждут решения о том, кто их делает

Пункт уже стоит в мастер-плане как открытый. Пока нет ответа, девять каталогов заполнять нечем: машинный перевод без ревью носителем даст худший результат, чем честный английский по умолчанию.

Блокер Копии стеков ждут решения о консистентности тома

Открытый вопрос мастер-плана. Без ответа, допустимо ли копировать том на работающем стеке или стек надо останавливать, проектировать функцию нельзя - от этого зависит и интерфейс, и гарантии, которые панель дает.

Блокер Правка P0-2 меняет контракт ответа

Перевод сообщений на ключи затрагивает поле msg в ack всех обработчиков. Нужно решить, остается ли msg техническим текстом для журнала при msgi18n: false, или поле целиком отдается под ключ. От этого зависит, сколько мест придется поменять и что увидит агент, подключенный к другой версии сервера.

Блокеры из-за невыбранной практики

Эти два пункта отличаются от предыдущих: препятствие не в коде и не в окружении, а в том, что решение о подходе никем не принято. Пока его нет, соответствующий этап плана начать нельзя.

Блокер Нет инструмента для юнит-тестов компонентов Vue

В package.json нет ни vitest, ни @vue/test-utils, ни DOM-окружения (jsdom, happy-dom). Все тесты идут на node:test с c8. Этап 6 плана требует решения: подключать DOM-окружение и @vue/test-utils к node:test, чтобы остался один раннер и одна цифра покрытия, или вводить vitest как второй. Первый вариант проще для CI, второй привычнее для фронтенда. Пока не выбрано, писать тесты компонентов не во что.

Блокер Нет политики совместимости сервера и агента

Версия контракта Socket.IO нигде не объявлена: агент любой версии подключается к серверу любой версии, и ни одна сторона это не проверяет. Этап 2 меняет формат поля msg в ack, и без правила, что делает новый сервер с ответом старого агента (принимает как есть, переводит, отклоняет), это изменение нельзя выкатывать на установки с несколькими узлами. Нужно либо объявить версию контракта в рукопожатии, либо зафиксировать, что сервер и агенты обновляются только вместе.

6. Что сейчас неизвестно и каких данных не хватает

Вопрос 1 Кто переводит каталоги

Варианты: профессиональный перевод, машинный с обязательным ревью носителем, или сокращение списка языков до тех, что реально поддерживаются. Без ответа заполнять 9 каталогов по 640 ключей бессмысленно.

Вопрос 2 RTL: верстаем или изымаем

Нужно решение: делать верстку под ar и ur в этом цикле, или убрать их из списка языков до готовности. Текущее состояние (язык предлагается, верстка не поддерживает) - худшее из трех.

Вопрос 3 Есть ли изолированное окружение для тестов

Нужен ответ: доступен ли отдельный хост или виртуальная машина, где можно запускать e2e и docker-integration, не задевая чужие стеки. Без этого часть правок проверяется только на уровне юнит-тестов.

Вопрос 4 Рантайм продакшена: tsx или сборка

Оставляем исполнение TypeScript через загрузчик или собираем бэкенд в JS при сборке образа. Второе дает проверяемый артефакт и более быстрый старт, но меняет Dockerfile и процесс выпуска.

Вопрос 5 Что делать с исключениями покрытия

Снимаем исключения в .c8rc.json и покрываем dockge-server.ts, agent-manager.ts и обработчики терминалов, или признаем их зоной ответственности e2e. Сейчас именно там найдены дефекты P0, и это аргумент в пользу первого варианта.

Вопрос 6 Приоритет мажорных обновлений

Делаем ли typescript 7 и express 5 в этом цикле или откладываем до закрытия функциональных задач мастер-плана. Цена мажорных обновлений - отдельный цикл проверок, а не полдня.

Вопрос 7 Куда писать причину сбоя Compose

В общий журнал сервера или в журнал конкретного стека, видимый пользователю. Второе полезнее, но требует уверенности, что в текст не попадут учетные данные из URL репозитория.

Вопрос 8 Данных нет по фактической нагрузке

Не измерено: сколько стеков и контейнеров у типичной установки, сколько занимает docker compose ls --all плюс docker ps на таком хосте, какова доля пустых записей в stack_observation за сутки. Эти три числа определяют, насколько срочны P1-1 и P1-3.

Вопрос 9 Заголовки безопасности

Сервер не ставит ни CSP, ни X-Frame-Options, ни другие защитные заголовки (helmet не подключен). Для панели за обратным прокси это обычно закрывает сам прокси, но по умолчанию продукт ставится и без него. Нужно решение, ставит ли заголовки само приложение; для CSP это отдельная работа, потому что Vue и CodeMirror используют inline-стили.
