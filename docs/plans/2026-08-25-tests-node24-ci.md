# Автотесты, Node.js 24 и обновление CI/CD

## Цель

Добавить исполняемые автотесты с порогом покрытия выше 60%, проверить совместимость проекта с Node.js 22.23.2 и 24.19.0, выбрать Node.js 24.19.0 как основной runtime после успешной проверки, включить строгую проверку TypeScript для исходников и тестов, а также обновить CI/CD и скрипты проекта.

## Ограничения и критерии готовности

- Разрешены только Node.js 22.23.2 и 24.19.0; основной локальный, контейнерный и CI runtime — 24.19.0 после проверки обеих версий.
- Тесты используют реальные SQLite, файловую систему, хеширование, модели и интеграционные границы приложения. Заглушки не применяются для обхода логики, ошибок базы данных или проверяемых ветвей.
- Команда покрытия завершает работу с ошибкой, если строки, функции, ветви или выражения не превышают 60%; целевой порог устанавливается с запасом и фиксируется в `package.json`.
- `check-ts` проверяет backend, common, frontend TypeScript/Vue SFC и тесты в строгом режиме без подавления ошибок исходников проекта.
- CI запускает линтер, строгую проверку типов, тесты с покрытием и сборку на обеих разрешённых версиях Node.js.
- Все изменения проходят локальную проверку на Node.js 22.23.2 и 24.19.0, затем проверяется чистый `npm ci` и отсутствие уязвимостей высокого уровня.

## Порядок выполнения

### 1. Проверить среду и зафиксировать политику Node.js

- Проверить доступность точного Node.js 24.19.0 в локальной среде; текущую совместимость сравнивать с уже установленным Node.js 22.23.2.
- Добавить `.nvmrc` со значением `24.19.0` и ограничение `engines.node` в `package.json`, допускающее только `22.23.2` или `24.19.0`.
- Обновить `CONTRIBUTING.md`, `docker/Base.Dockerfile` и workflow-файлы так, чтобы они использовали Node.js 24.19.0 по умолчанию, сохраняя отдельную проверку Node.js 22.23.2.

### 2. Сначала написать тестовый каркас и получить ожидаемый RED-результат

- Добавить `c8` как инструмент покрытия и использовать встроенный `node:test` через существующий `tsx`, не добавляя тяжёлый тестовый фреймворк без необходимости.
- Создать тестовые вспомогательные функции для временной директории и реальной временной SQLite-базы; очистка выполняется через `finally`, чтобы тесты не зависели от порядка запуска.
- Создать тесты для `common`, базы данных, настроек, моделей пользователей и агентов, хеширования паролей и выбранных чистых функций backend. Проверять успешные сценарии, ошибочные входные данные, отсутствие записей, обновления и удаление.
- Добавить интеграционный тест Socket.IO/HTTP только там, где он не требует обхода авторизации или файловой логики; соединение, события и ответы должны проходить через реальные объекты проекта.
- Запустить тесты до реализации новых команд покрытия и строгой конфигурации, зафиксировать фактические причины падений, а не скрывать их настройками.

### 3. Реализовать тесты и устранить найденные ошибки

- После RED-результата добавить только необходимые исправления production-кода, сохраняя текущий контракт приложения.
- Подключить покрытие всех загруженных production-модулей и явно включить проверяемый набор `backend/**/*.ts` и `common/**/*.ts`; исключить только миграции, конфигурационные точки входа и сгенерированные файлы, если их невозможно исполнять в изолированном тесте.
- Зафиксировать пороги покрытия выше 60% в скрипте CI и локальной команде; HTML и lcov отчёты складывать в игнорируемый каталог.
- Проверить, что тесты не используют `any`, не отключают строгую проверку и не подменяют функции, чьё поведение измеряется.

### 4. Включить строгую проверку всего TypeScript/Vue-кода

- Расширить конфигурацию TypeScript на backend, common, frontend TypeScript/Vue SFC и тесты.
- Подключить `vue-tsc` для проверки шаблонов и скриптов Vue, отключить базовые послабления TypeScript и устранить реальные ошибки типов в исходниках.
- Проверить совместимость выбранной версии TypeScript с актуальным `typescript-eslint` и не обновлять TypeScript 7 до появления совместимой цепочки инструментов.

### 5. Оптимизировать команды npm и CI/CD

- Добавить единые команды `test:unit`, `coverage` и `check`, чтобы локальная и CI-проверка использовали один набор проверок.
- Удалить только подтверждённые неиспользуемые команды или дублирующие обёртки; команды выпуска, Docker и обслуживания сохранить, если они вызываются документацией, workflow или другим скриптом.
- Обновить GitHub Actions до актуальных основных версий, добавить Node.js 24.19.0 и проверку Node.js 22.23.2, включить тесты с покрытием в обязательный CI.
- Обновить проверку YAML/JSON и Docker actions до актуальных версий, добавить минимальные права workflow и тайм-ауты там, где это не меняет предназначение pipeline.

### 6. Финальная проверка

- На Node.js 22.23.2 выполнить `npm ci`, `npm run lint`, `npm run check-ts`, `npm run test`, `npm run coverage` и `npm run build:frontend`.
- На Node.js 24.19.0 повторить тот же набор и проверить запуск backend smoke-тестом.
- Выполнить `npm ci --dry-run`, `npm audit --audit-level=high` и проверить diff workflow, Docker и package-lock.
- Сверить план с фактическим состоянием ветки и сообщить пользователю изменённые файлы, процент покрытия, результаты обеих версий Node.js и оставшиеся ограничения.
