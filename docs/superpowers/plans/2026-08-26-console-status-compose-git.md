# План: консоль контейнера, статусы, Compose-файлы и Git-деплой

> Исполняемый план для рабочей ветки `mzx/dependency-stack-review`. Все задачи выполняются с реальными файловыми, браузерными и Docker Compose-проверками; заглушки, обходящие проверяемую логику, запрещены.

## Цель

Устранить четыре связанные группы проблем в Dockge2:

1. сделать вставку в контейнерную консоль рабочей через `Ctrl+V`, `Ctrl+Shift+V`, `Cmd+V` и контекстное меню;
2. сделать переключение между `sh` и `bash` настоящей сменой PTY-сессии;
3. показывать состояние каждого сервиса и экземпляра, отделяя предупреждение от полностью остановленного стека;
4. добавить явный выбор Compose/env-файлов и безопасную работу с `.secret`, а также перестать повреждать исходный YAML при редактуре и Git-деплое.

## Архитектура и границы

- Vue 3/Vite остаются фронтенд-стеком, Express/Socket.IO — транспортом бэкенда.
- Для Compose используется установленный Docker Compose CLI; не добавлять отдельный Compose-парсер и не дублировать его семантику.
- `yaml` используется для проверки и структурных операций только там, где это не ломает исходный документ. Исходный YAML хранится и передаётся как текст до явного редактирования.
- Выбор shell, Compose-файла, env-файлов и secret-файлов проходит через типизированные модели и серверную валидацию.
- Git/Docker-обновление остаётся локальным CLI/операционной процедурой и не превращается в браузерный API произвольного запуска команд.

## Технологические решения

- Shell: закрытый тип `"sh" | "bash"`; произвольные аргументы shell из браузера запрещены.
- Вставка: публичные API xterm.js и системное `paste`-событие; `document.execCommand("paste")` не использовать.
- Статусы: отдельный `ATTENTION` вместо маскировки частичного или неизвестного состояния под `inactive`.
- Env: CLI `--env-file` для интерполяции Compose отделён от `services.*.env_file`.
- Secrets: отдельные Compose secrets, файл `.secret` не превращается автоматически в переменные окружения.
- YAML: `docker compose config` используется для проверки/просмотра, но его канонический вывод никогда не записывается обратно в исходный файл без явного действия пользователя.
- Git: аргументы передаются массивом в уже существующий процессный слой; `shell: true`, `git reset --hard`, `git clean -fdx`, `docker compose down -v` и `docker volume prune` запрещены.

## Зафиксированные ограничения

- Имена файлов — только безопасные относительные имена внутри каталога стека: без абсолютных путей, `..`, обратного обхода каталога и симлинков.
- Содержимое secret-файлов не попадает в обычный `getStack`, журналы, тексты ошибок, список стеков и диагностические сообщения.
- При отсутствии разрешения Clipboard API пользователь получает понятный fallback/сообщение; ошибка не проглатывается молча.
- Рабочая консоль не должна писать в логи содержимое вставки или выделения.
- Успешно завершившийся одноразовый worker/init не считается причиной объявлять стек мёртвым; ненулевой выход одноразового сервиса остаётся предупреждением.
- Все новые публичные модели и обработчики имеют строгие типы TypeScript; `unknown` сужается явно, а не заменяется `any`.
- Acceptance-тесты проверяют результат операции: фактический текст в PTY, фактическое состояние контейнера, содержимое файлов и реальный вызов Compose.

## Задача 1. Надёжная вставка в контейнерную консоль

### Изменяемые файлы

- `frontend/src/components/Terminal.vue` — общий xterm-компонент, обработчики клавиш, `paste` и копирования.
- `frontend/src/components/TerminalContextMenu.vue` — небольшое контекстное меню с действием «Вставить» и закрытием по Escape/клику вне меню; единый обработчик вставки передаётся через типизированный callback.
- `frontend/src/i18n.ts` и файлы локализации — подписи, подсказки и ошибка разрешения буфера.
- `test/e2e/terminal-paste.spec.ts` — реальный браузерный тест интерактивной консоли.
- `playwright.config.ts` и `test/e2e/fixtures/` — конфигурация Chromium, разрешений Clipboard API и запуска приложения для сквозных тестов.

### Реализация

1. Развести три сценария:
   - `Ctrl+V`/`Cmd+V` и `Ctrl+Shift+V` распознаются через `attachCustomKeyEventHandler` без двойной отправки символа `v` в PTY;
   - обычное `paste`-событие xterm остаётся резервным путём для браузера и ОС;
   - правая кнопка открывает явное меню, где «Вставить» вызывает тот же типизированный обработчик, а не отдельную копию логики.
2. Сначала использовать `navigator.clipboard.readText()` из пользовательского действия. При отказе разрешения не отправлять пустую строку: показать понятное состояние и оставить доступным нативный `paste`-путь xterm.
3. Передавать в terminal controller исходный текст без обрезания, нормализации пробелов или удаления переводов строк. Для интерактивного PTY использовать публичный `terminal.paste(text)`/эквивалент текущей версии xterm; для ограниченной консоли сохранить правило «вставка не нажимает Enter автоматически».
4. Не использовать скрытое поле вне xterm, `execCommand("paste")`, запись буфера в `console.log` или отправку текста в URL/Socket.IO-событие для диагностики.
5. Проверить, что выделение и копирование не отправляют содержимое выделения в логи и не превращают правый клик в немедленную вставку без выбора пользователя.

### Проверки

- Реальный Chromium в Playwright с разрешением Clipboard API: вставить строку с пробелами, кавычками, `$`, обратными слешами и переводом строки через `Ctrl+V`.
- Отдельно проверить `Ctrl+Shift+V`, `Cmd+V` в контексте macOS-совместимого события и пункт контекстного меню.
- Проверить, что в PTY приходит ровно исходный текст, а Enter выполняется только отдельным нажатием.
- Проверить отказ в доступе к буферу без подмены `navigator.clipboard`: интерфейс показывает ошибку/fallback, приложение не падает и не отправляет пустой ввод.
- Проверить отсутствие двойной вставки при сочетании `Ctrl+Shift+V` и нативного `paste`-события.

### Критерий готовности

Все четыре пользовательских способа вставки проходят на реальной странице и приводят к одному ожидаемому содержимому PTY; тест не заменяет Clipboard API, xterm или Socket.IO заглушкой.

## Задача 2. Настоящее переключение `sh`/`bash`

### Изменяемые файлы

- `common/util-common.ts` или новый `common/terminal.ts` — `ContainerShell`, имя сессии и общие типы.
- `frontend/src/pages/ContainerTerminal.vue` — shell selector/ссылка, состояние текущего shell, обработка перехода и ошибки.
- `frontend/src/components/Terminal.vue` — передача shell/session identity и корректное закрытие клиента.
- `backend/terminal.ts` — ключи PTY, завершение/отсоединение и защита от переиспользования PTY другого shell.
- `backend/agent-socket-handlers/terminal-socket-handler.ts` — allow-list shell, проверка стека/сервиса и события `terminalLeave`.
- `backend/stack.ts` — запуск только разрешённого исполняемого файла после проверки существования контейнера/сервиса.
- `test/integration/terminal-shell.test.ts` и `test/e2e/container-terminal.spec.ts` — интеграционные и браузерные проверки.

### Реализация

1. Заменить свободную строку `shell` на `ContainerShell = "sh" | "bash"`; любое другое значение отклонять до обращения к Docker.
2. Включить shell и идентификатор клиента/сессии в ключ терминала. При переходе `sh → bash` старый клиент явно посылает `terminalLeave`, новый получает отдельную сессию, а общий PTY закрывается только когда у него не осталось клиентов.
3. Обработать разрыв Socket.IO и размонтирование Vue одинаково; отсутствие leave-события не должно оставлять бесконечный PTY.
4. Проверять имя стека и сервиса по реально загруженной конфигурации стека до запуска `docker compose exec`; не разрешать браузеру передавать произвольную команду или произвольный путь к shell.
5. Кнопку сделать динамической и честной: показывать доступный целевой shell, не переиспользовать сессию с прежним shell и отображать ошибку, если `bash`/`sh` отсутствует в образе.

### Проверки

- Реальный Compose-фикстурный контейнер с `/bin/sh` и `/bin/bash`: обе сессии получают разные идентификаторы и правильный shell.
- Попытки `zsh`, `bash -c ...`, неизвестного сервиса и неизвестного стека отклоняются до запуска процесса.
- После переключения ввод в старой сессии не появляется в новой, а завершённая сессия освобождает PTY.
- Открыть две вкладки одного shell и убедиться, что уход одной не завершает сессию другой.
- Браузерный тест проверяет, что `Switch to sh` действительно меняет prompt/идентичность сессии, а не только URL.

### Критерий готовности

Название и состояние терминала однозначно определяют shell и клиентскую сессию; переключение подтверждается реальным PTY и не расширяет API до произвольного выполнения команд.

## Задача 3. Детальный статус контейнеров и состояние `ATTENTION` — выполнено 2026-08-26

Проверено unit-тестами (`test/common/compose-status.test.ts`, `test/backend/stack-status.test.ts`), реальным Docker Compose (`test/backend/stack-docker.integration.test.ts`) и живым прогоном UI в браузере.

**Уточнение модели, принятое при реализации:** одноразовый жизненный цикл задаётся явно, поэтому неразмеченный `exited(0)` рядом с работающим сервисом даёт `ATTENTION` с причиной `serviceStopped`, а не `RUNNING`. Требование issue #806 («не показывать такой стек остановленным») выполняется, но льгота до `RUNNING` даётся только при явной пометке. Compose трактует ключи `x-*` внутри сервиса как расширения и не передаёт их в метки контейнера, поэтому поддержаны три записи: `x-dockge: { lifecycle: one-shot }`, плоский ключ `x-dockge.lifecycle` и метка контейнера `dockge.lifecycle=one-shot`.

**Отложено на задачу 6 и Task 0:** браузерный e2e-тест (`test/e2e/stack-status.spec.ts`) появится вместе с Playwright. Найденные при живом прогоне pre-existing дефекты `Container.vue`: в шаблоне используются необъявленные `ports` и `processing`, из-за чего кнопки сервиса не блокируются во время операции; CodeMirror получает boolean-props строками.

### Модель и правила

Каждый экземпляр хранит минимум `service`, `name`, `state`, `health`, `exitCode`, `statusText`, `isOneShot` и причину предупреждения. Агрегатор не использует `serviceStatus[0]` и не выводит статус по одной строке `docker compose ls`.

| Фактическое состояние | Статус стека |
|---|---|
| Все долгоживущие сервисы работают/здоровы; clean-exit one-shot разрешён явно | `RUNNING` |
| Есть работающие сервисы, но другой экземпляр `N/A`, отсутствует, `restarting` или неизвестен | `ATTENTION` |
| Есть `unhealthy` или ненулевой exit code у любого отслеживаемого сервиса | `ATTENTION` |
| Явно отмеченный `x-dockge.lifecycle: one-shot` завершился с кодом 0, долгоживущий сервис работает | `RUNNING` |
| Такой worker/init завершился с ненулевым кодом | `ATTENTION` |
| Работающих сервисов нет, экземпляры завершены | `EXITED` |
| Экземпляры только созданы и ещё не запущены | `CREATED` |
| Docker недоступен, JSON повреждён или данных недостаточно для вывода | `UNKNOWN` |

Имена `worker`, `init`, `job` сами по себе не дают льготы: одноразовый жизненный цикл задаётся явной меткой Compose (`x-dockge.lifecycle: one-shot`) либо настройкой стека.

### Реализация

1. Выполнять `docker compose ps --all --format json` с выбранным `-f` и выбранными env-файлами; поддержать формат одной JSON-строки на контейнер и JSON-массив.
2. Нормализовать `State`, `Health`, `ExitCode`, отсутствие поля и текст статуса в `ContainerInstanceStatus`; неизвестные значения не считать `RUNNING`.
3. Группировать по сервису, затем вычислять статус стека по таблице выше. Отдельно возвращать `issues[]`, чтобы UI объяснял `ATTENTION`.
4. Кнопки start/stop/restart включать по статусу конкретного сервиса/экземпляра, а не по первому элементу массива.
5. Не выдавать `N/A` как `inactive`: это причина предупреждения или `UNKNOWN`, пока не доказано обратное.

### Проверки

- Реальный Compose-сценарий: работающий сервис плюс worker, завершающийся с кодом 0; ожидается `RUNNING`.
- Сценарий с worker, завершающимся с ненулевым кодом; ожидается `ATTENTION` с именем и кодом.
- Сценарии с остановленным сервисом, `unhealthy`, `restarting`, отсутствующим экземпляром и смешанными репликами; ни один не маскируется под обычный `inactive`.
- Повреждённый/неполный вывод и недоступный Docker дают `UNKNOWN` с безопасным UI-сообщением.
- Браузер проверяет предупреждающий значок, tooltip/детали и то, что здоровый сервис не получает надпись «мёртв» из-за отдельного worker.

### Критерий готовности

Пользователь видит статус каждого сервиса и экземпляра; частичная деградация отображается как внимание с причиной, а полностью остановленный стек — только когда это подтверждено всеми отслеживаемыми сервисами.

### Модель хранения

В метаданных стека хранить только выбор и порядок файлов, например `composeFileName`, `envFileNames[]`, `activeEnvFileName` и `secretBindings[]`. Сами тексты остаются в файлах каталога стека. Secret content не включать в `Stack`-ответ.

Поддержать безопасные имена файлов вроде `.env`, `.env.product`, `.env.dev`, `.env-test`, `.secret`, `.secret.db`; расширение списка допустимых имён делать явным и тестируемым, а не разрешать произвольный путь. Текущие `compose.yaml`, `docker-compose.yaml`, `docker-compose.yml`, `compose.yml` сохранить для миграции.

Если в старом стеке найден ровно один подходящий Compose-файл, выбор можно перенести автоматически. Если вариантов несколько и метаданных нет, UI обязан показать выбор/состояние «нужно выбрать», а сервер не должен молча переключаться между файлами.

### Реализация

1. Ввести единый `resolveStackFilePath(stackDir, fileName)`: проверить относительность, нормализованный путь, отсутствие `..` и симлинка; после проверки убедиться, что итоговый путь остаётся внутри каталога стека.
2. Для Compose-команд всегда передавать выбранный файл явно через `-f`. Для интерполяции передавать упорядоченные `--env-file`; `.env` не считать обязательным, если выбран другой файл.
3. Не менять YAML-поле `services.*.env_file`: оно описывает переменные внутри контейнера и остаётся частью Compose-документа. UI подписью и типами разделить его с CLI env-файлами.
4. Для `.secret` добавить отдельное действие создания/обновления/очистки/удаления. При сохранении на POSIX выставлять режим `0600` с учётом текущего пользователя процесса; на Windows применить поддерживаемый ACL-механизм или безопасно сообщить о невозможности усилить права.
5. Связывать secret с Compose только явным действием пользователя: создать/изменить верхнеуровневый `secrets` и `services.<service>.secrets`, сохранить имя и путь без содержимого. Не превращать `.secret` в `environment` или CLI env автоматически.
6. В обычном списке стеков и `getStack` возвращать имена, размеры, время изменения и факт наличия secret без содержимого. Раскрытие/редактирование требует отдельного права и отдельного события; по умолчанию UI показывает маску.
7. Проверить очистку: пустой env-файл удаляется только по согласованному правилу существующего PR #979; пустой secret-файл не раскрывается через ответ API и не остаётся с неожиданными старыми данными.

### Проверки

- Реальные временные каталоги: `.env`, `.env.product`, `.env.dev` и `.secret` читаются по выбранной конфигурации, а файл вне каталога, абсолютный путь и симлинк отклоняются.
- Реальный Compose-проект с двумя env-файлами показывает, что выбранный порядок влияет на интерполяцию, а `services.*.env_file` продолжает работать по YAML-семантике.
- Реальный контейнер получает Compose secret по `/run/secrets/<name>`; секрет не появляется в обычном Stack JSON, логах или тексте ошибки.
- Проверить ротацию и удаление secret, режим файла на POSIX и отказ неавторизованного действия.
- Браузерный тест выбирает основной YAML, `.env.product`, `.env.dev` и `.secret`, затем проверяет сохранённые метаданные и маскирование.

### Критерий готовности

В каталоге можно безопасно хранить несколько Compose/env/secret-файлов, Dockge использует выбранные файлы явно, а секрет доступен контейнеру только после явной привязки и не утечёт через обычный API.

## Задача 5. Сохранение исходного YAML и безопасный Git-деплой — выполнено 2026-08-27

**Найденная причина порчи YAML:** watcher `jsonConfig` в `Compose.vue` пересобирал файл через `new Document(jsonConfig)` при любом изменении модели, включая простое открытие страницы и обновление статуса, а `NetworkInput.applyToYAML()` безусловно присваивал `networks = {}` при монтировании. Поэтому терялись комментарии, anchors/aliases, merge-ключи, кастомные теги и octal-запись, а в файл добавлялся пустой `networks`.

**Что сделано:** новый `common/compose-editor.ts` анализирует исходник (`include`, anchor, alias, merge key, кастомные теги, ошибки разбора) и применяет структурную правку точечным diff-ом к документу исходника, восстанавливая legacy octal. Запись текста разрешена только при явной правке: watcher теперь выходит, если правит текстовый редактор, если данные пришли с сервера, если страница в режиме просмотра или если файл нельзя пересобрать. Для таких файлов структурные блоки (контейнеры, сети, extra) скрыты и показан баннер с перечнем конструкций. `NetworkInput` больше не создаёт `networks: {}` и сообщает явное удаление последней сети. Перед каждым `up` (`deploy`, `start`, `update`) выполняется `docker compose config --quiet` с выбранными `-f`/`--env-file`; при ошибке запуск не происходит, канонический вывод `config` никуда не сохраняется. Добавлен CLI `npm run deploy-stack` для обновления одного стека из Git: проверка чистоты каталога, `pull --ff-only`, `config --quiet`, `up -d --pull always --wait`, без `reset`/`clean`/`down -v`, с валидацией имени стека, ветки и имён файлов.

**Проверено:** unit-тесты `test/common/compose-editor.test.ts` и `test/backend/deploy-stack.test.ts`, серверные тесты `test/backend/compose-source-preservation.test.ts` (чтение и сохранение не меняют байты), реальный Docker (`config --quiet` отклоняет невалидный проект и контейнеры не создаются). Живой прогон в браузере: файл с anchor/alias/merge key/octal остался байт-в-байт после открытия, входа в режим редактирования и сохранения, а на простом файле добавление сервиса дало ровно одну добавку без потери комментариев и без `networks: {}`.

**Не сделано в этой задаче:** серверный Git-адаптер для Git-стеков как продуктовой функции (`backend/git-compose-deploy.ts`) не добавлен, потому что Git-стеки ещё не входят в интерфейс; операционный сценарий закрыт CLI. Браузерные тесты `test/e2e/git-compose.spec.ts` ждут Playwright из задачи 6.

### Исправление YAML и `networks: {}`

1. Хранить исходную строку YAML как source of truth. Парсить её для подсказок и просмотра, но watcher статуса, загрузка env, открытие страницы и Git-refresh не должны сериализовать `new Document(...).toString()` обратно в `stack.composeYAML`.
2. Ввести явные причины изменения: `raw-edit`, `structured-edit`, `external-refresh`. Только `raw-edit` и подтверждённый `structured-edit` могут менять исходный текст.
3. `NetworkInput.applyToYAML()` должен:
   - не добавлять `networks`, если в исходнике его не было и пользователь ничего не добавил;
   - удалять пустой ключ только после явного удаления последней сети;
   - записывать непустой объект только когда пользователь действительно добавил/изменил сеть;
   - не трогать комментарии, YAML-теги и соседние поля без необходимости.
4. Для `include`, `!reset`, `!override` и неизвестных YAML-тегов использовать round-trip-документ. Если структурный редактор не может сохранить конструкцию без изменения смысла, отключать конкретное структурное действие и оставлять текстовый режим, а не silently reserialize.
5. `docker compose config --quiet` использовать перед deploy как проверку. Полный `docker compose config` разрешён для отдельного preview, но его `networks: {}` и прочие значения по умолчанию не записываются в исходный YAML.

### Git-процесс

Текущий checkout не содержит законченного Git-deploy-модуля, поэтому реализацию считать новым граничащим компонентом, а не исправлением уже существующего обработчика.

1. Конфигурация Git-стека должна содержать репозиторий, ветку/commit, каталог, основной Compose-файл, порядок env-файлов и secret bindings. В браузер передавать только заранее сохранённые идентификаторы/имена, не произвольную команду.
2. Перед обновлением проверить рабочее дерево и состояние конфигурации. При локальных изменениях остановиться с объяснением; не применять `reset --hard` и не удалять файлы пользователя.
3. Выполнить `fetch`/`pull --ff-only` через аргументный процессный слой, проверить ожидаемый commit и заново загрузить выбранный Compose/YAML/env. Сбросить кэш стека до запуска Compose, чтобы старое содержимое из памяти не перезаписало Git-версию.
4. Запустить проверку с теми же аргументами, что и deploy: `docker compose -f <file> [--env-file <env-file>]... config --quiet`. При ошибке не выполнять `up` и не сохранять канонический вывод.
5. Запустить `docker compose -f <file> [--env-file <env-file>]... up -d --pull always --wait --wait-timeout 60`; `--force-recreate` оставить отдельной осознанной опцией. Bind mounts и named volumes не удалять.
6. Если нужен временный checkout для Git-операции, удалять только известный временный worktree после успешного/неуспешного завершения; не использовать широкое удаление по glob и не трогать каталог данных.
7. Все логи редактировать до вывода: не печатать токены, пароли, содержимое env/secret, URL с credentials и полный набор секретных аргументов.

### Проверки

- YAML-фикстура без `networks`: открытие, просмотр, env-refresh и сохранение без правки не добавляют `networks: {}`.
- Фикстуры с комментариями, `include`, `!reset`, `!override`, `yes/no/on/off`, `tmpfs.mode: 01777` проходят round-trip без изменения смысла.
- Явное добавление сети создаёт ключ; явное удаление последней сети удаляет или изменяет его согласно выбранному контракту; служебный watcher не считается явным действием.
- Git-фикстура с двумя YAML-файлами проверяет, что UI и Compose используют один выбранный файл, а `config --quiet` не перезаписывает его.
- Ветка с локальными изменениями, не-fast-forward, ошибкой Compose и ошибкой Docker не приводит к `up`, потере YAML или удалению пользовательских данных.
- Реальный bind mount после пересоздания контейнера сохраняет контрольный файл; это проверяет именно сохранность данных, а не только успешный exit code.

### Критерий готовности

Git обновляет выбранный Compose-проект безопасно, исходный YAML остаётся исходным текстом, `networks: {}` появляется только по явной семантике документа/действию пользователя, а не из-за просмотра или деплоя.
