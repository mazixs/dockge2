# Dockge2 0.0.14

This release lets an owner update the panel from Settings -> About. The page stays open through the
restart and ends on a clear result: updated, not updated with the old version still running, not
installed with the previous version running again, or needs attention on the host. The update runs
the same verified updater as on the host, and when the new version does not become ready the
updater brings the previous one back, restoring the data snapshot if the schema changed.

It also shows the containers Dockge does not manage, recognises the panel's own container, replaces
the `docker run` converter with one of its own, and sends a Content Security Policy with every
answer.

## Updating

This update still runs on the host; use the actual installation directory:

```bash
sudo /opt/dockge2/.dockge2/update --version 0.0.14 --dry-run
sudo /opt/dockge2/.dockge2/update --version 0.0.14 --yes
```

It installs the updater that the web interface drives, so the next release can be installed from
About. No stack files change, and the database schema is the same as in 0.0.13. See
[updating](https://github.com/mazixs/dockge2/blob/v0.0.14/docs/updating.md).

## Updates from the web interface

- About -> **Prepare update to <version>** runs the updater's dry run: the release is verified and the page shows
  the current and target versions, the configuration fields that change and whether the database
  schema changes. Nothing is downloaded or changed.
- **Update to <version>**, confirmed with the owner's password within ten minutes of the check,
  starts the updater in a short-lived container of the panel's own image, outside the Compose
  project, so it survives the panel stopping. The installation and the data directory are mounted
  read-only; only the updater's own state is writable.
- The page follows the steps - download, stop, save data, start, verify - and stays on screen while
  the panel restarts. It reloads into the new version only after the updater confirmed the result
  and the panel that answers runs the target version.
- The download can be cancelled; from the stop on the update runs to its end. Other signed-in users
  see a banner instead of an unexplained disconnect.
- A reloaded tab picks the progress up again once the panel answers. If the updater was killed
  without a result, the page reads its journal - only the journal of that update, never of an
  earlier one - and shows the commands for the host.
- A tab left open on the old version through someone else's update loads the new version before
  it shows the result.
- A check that the page stops hearing about asks the panel again after a minute, says that it is
  taking longer than usual, and keeps waiting while Docker cannot be read.
- Only an owner starts, cancels or closes an update, and no agent or MCP key can. Installations the
  updater does not manage, and updaters older than this release, keep the host commands.

## Updater

- `--progress json` prints each phase and exactly one result as JSON lines, for updates, dry runs
  and `--status`. A result carries the outcome, the phase, the operation and a single redacted line
  of error.
- `--restore-on-failed-start`: when the schema changed and the new panel never became ready, the
  updater restores the verified data snapshot and starts the previous panel instead of stopping at
  `recovery-required`. The data the failed version wrote is kept as `*.dockge-failed-<operation>`.
  Updates from the web interface always pass it.
- Data restoration, automatic or with `--rollback --restore-data`, runs in a short-lived container
  of the previous image with no network and a read-only root. A data directory directly under `/` or
  under `/tmp` is refused. When the restore fails or runs out of time the updater removes that
  container; if it cannot confirm the removal, the journal stays `rolling-back` rather than claiming a
  final state.
- `--resume` refuses an operation whose data snapshot was restored or whose restore began, so the
  new version cannot migrate the restored data a second time; `--rollback --restore-data` finishes it.
- `--status` of a recovered operation says whether the data snapshot was restored.
- Updating to the version already running, with the same image and configuration, finishes without
  a restart.
- SIGTERM before the panel is stopped ends the update and leaves the running panel as it was; after
  that the updater finishes the update or its recovery.
- The signature verifier keeps its cache under `.dockge2/cosign`.

## Stacks and containers

- The list also searches the images of the services and the server name. The search text stays in
  the address (`?q=`) next to the filter, so a narrowed list survives opening a stack and a reload.
- Each server shows 50 stacks and a **Show N more** button; the open stack stays visible past the
  limit.
- A stack page shows how its services relate: dependencies, networks, ports, mounts and secrets,
  read from the stack's own files, so stopped services and override files count. Environment values
  never leave the server.
- Containers started without Compose, and Compose projects outside the stacks directory, are listed
  with their state. Each container has a page with its image, health, start time, restarts, ports,
  networks and mounts. When Docker stops answering they turn unknown with the time they were last seen instead of
  disappearing.
- An owner can let operators start, stop and restart those containers, per server, in Settings ->
  Security, confirming with the password. It is off by default. The server checks the container
  again before each command and refuses stack containers and the panel's own. Removing, killing and
  opening a shell are not offered.
- The panel recognises its own container by its id, never by name. When its compose file lies in the
  stacks directory, down, delete, start, restart, deploy and update are refused on it, since each
  would remove the container that runs the command; stop stays, with a warning. Settings -> About
  shows the panel's container read-only: image and digest, health, uptime, restarts, mounts, and
  whether the Docker socket is mounted, with what that means.
- A remote agent can be renamed from its row in Settings -> Agents.

## Docker run to Compose

- The converter behind **Create from docker run** is now the panel's own. It knows every flag of
  `docker run`, and each one is either written to the file or named in the report with the reason.
  It adds no `version`, default network, `privileged` or `container_name` you did not ask for, and
  `no`, `yes`, `22:22` or `0755` stay strings.
- On a corpus of 51 real commands every result passes `docker compose config`; the previous
  converter produced files Compose rejected for 5 of the first 39. `docker container run` is
  accepted too.
- The production install is about 13 MB smaller without the old converter's dependencies.

## Security

- Every answer carries a Content Security Policy that allows scripts from the panel only and
  refuses framing, with `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and
  `Cross-Origin-Opener-Policy`. A reverse proxy that injects its own scripts into the pages will be
  blocked.
- [The Docker socket and what the panel can do](https://github.com/mazixs/dockge2/blob/v0.0.14/docs/threat-model.md)
  explains why the socket is root on the host, why `:ro` does not change that, and every path to it
  through the panel.
- An MCP key can be reissued: the new secret keeps the servers, stacks, mode and lifetime, and the
  old one works 24 more hours or until it expires, whichever comes first. The access log records it.
- The MCP endpoint says why it refused a request: an origin that is not allowed, or a key that needs
  an owner.

## Interface

- Every request the interface waits for has a deadline. A deploy or update whose answer is lost
  reads the stack state again instead of repeating the command.
- Refusals of the server are translated: "Stack not found", "The stack has no service x" and about
  forty others used to arrive as an English sentence under "Unexpected error". A confirmation is no
  longer translated twice, which showed it as an unexpected error too. An agent of an earlier
  release still sends some refusals in English.
- Dates and times follow the language of the interface, not the browser's.
- Sixty page loads in a row from one address, such as a team behind a proxy without
  `DOCKGE_TRUST_PROXY`, no longer lock the interface behind "The server did not respond": reading
  one's own session is not rate limited.
- The overview's counters tell a screen reader which filter is active, and Lighthouse finds no
  accessibility issue on the dashboard, a stack, its files, the create form, About or Security.
- Measured on 2000 containers across 300 stacks with the CPU slowed four times: filtering the list
  stays under 140 ms at the 95th percentile, a status refresh redraws no row, and memory does not
  grow over repeated use.

## Agents

A panel of 0.0.14 works with agents of earlier releases. Such an agent reports no containers
outside its stacks, so neither the group nor the controls appear for it, and the messages it sends
in the former wording are still translated.
