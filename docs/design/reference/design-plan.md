# Dockge2: дизайн-система 0.1 и план внедрения

Дата: 2026-09-13. Статус: предложение на утверждение пользователем. Реализация приложения в этой задаче не изменяется.

## Решение

Выбранный "Знакомый Dockge" остается визуальным направлением. Следующий шаг - локальная система правил и компонентов, проверенная на трех основных сценариях. Не начинать новую серию точечных CSS-правок до согласования этой системы.

Разделяем три артефакта:

1. `index.html` - зафиксированный эталон Sites 01, без внешней презентационной оболочки. Его оформление не улучшаем задним числом.
2. `system.html`, `proposal.css` и этот документ - предлагаемая дизайн-система, состояния и согласованные отличия от эталона.
3. `test/visual/` - настоящие компоненты приложения на изолированных данных; после согласования здесь проверяется внедрение. Экспорт React/Tailwind не переносится в Vue-приложение как новый набор зависимостей.

Так эталон не зависит от авторизации, обновлений оболочки Sites и сети; предложение не подменяет оригинал; приемка использует настоящий код.

## Происхождение эталона

Источник: https://dockge2-design-directions.xizam.chatgpt.site/, версия 1. Коммит `7bce7fcfa312f93583fcfe57c7d247af679c43d4` подтвержден через Sites `list_site_versions` и совпадает с локальным исходным проектом. `provenance.json` содержит SHA-256 исходных HTML/CSS/JS/шрифтов. `export.py` повторяет экспорт из найденного исходного проекта. Исходный сайт не изменялся и не публиковался заново.

Перенесены готовые клиентские ресурсы, а не HTML страницы входа и не скриншот вместо интерфейса. `standalone.css` исключает только внешние панели, рамку и ее отступы. `navigation.js` добавляет навигацию по демонстрационным экранам и подпись вне рабочей области. Внутри пакета сохранены исходные клиентские зависимости для воспроизводимости; они не являются предлагаемой архитектурой Dockge2.

Эталон запускается обычным статическим HTTP-сервером. Открытие через `file://` не является поддерживаемым режимом: модульные ресурсы используют корневые пути. Все ресурсы находятся локально; Docker, Git и вход через Sites не нужны.

## Шрифты и шкала

Использовать **IBM Plex Sans** для всего интерфейса, **IBM Plex Mono** для кода и технических идентификаторов. Оба уже есть в Sites и приложении; замена шрифта не решает расхождения плотности.

| Токен / назначение | Семейство | Вес | Размер / строка при базе 16 px |
| --- | --- | --- | --- |
| page-title | IBM Plex Sans | 600 | 1.875rem / 2.25rem (30/36), tracking -0.7 px |
| section-title-large | IBM Plex Sans | 500 | 1.375rem / 1.875rem (22/30) |
| section-title | IBM Plex Sans | 500 | 1rem / 1.5rem (16/24) |
| body | IBM Plex Sans | 400 | 1rem / 1.5rem (16/24) |
| ui, важные состояния, кнопки | IBM Plex Sans | 400 или 500 по роли | 0.875rem / 1.25rem (14/20) |
| metadata, пояснение поля | IBM Plex Sans | 400 | 0.75rem / 1.125rem (12/18) |
| code | IBM Plex Mono | 400 | 0.8125rem / 1.3125rem (13/21) |
| short-hash | IBM Plex Mono | 400 | 0.75rem / 1.125rem (12/18) |

В исходном эталоне сохраняются его 10-13 px. В предлагаемой системе важные статусы и действия повышаются до 14 px, вторичные подписи не опускаются ниже 12 px. Это явное отклонение на согласование. Не добавлять третий шрифт или искусственный bold. Увеличение текста до 200% не блокируется.

WOFF2 поставляется локально: кириллица и латиница, Sans 400/500/600, Mono 400; сохранить OFL-лицензии. Определить понятные fallback-цепочки: Sans -> system-ui -> sans-serif, Mono -> ui-monospace -> monospace. Подгрузку и метрики проверить при холодном входе, чтобы не было сдвига размеров. Не подключать внешние шрифтовые сервисы.

## Токены, темы и геометрия

Три уровня: исходные значения -> семантические роли -> параметры компонента. Например, палитра -> `surface-panel` -> фон карточки источника. Компонент использует роль, не выбирает собственный hex-код. В приложении остается один источник значений `frontend/src/styles/tokens.scss`; после согласования каталог должен использовать тот же источник, не параллельную ручную копию.

Темная основа: base `#111419`, sidebar `#151920`, panel `#191d24`, raised `#232832`, text `#ecedf2`, secondary `#9ba3b2`, accent `#9dacf9`, running `#78d5a8`, changes `#edbf7b`. Светлая тема сохраняет ту же структуру: base `#f4f6f8`, panel `#ffffff`, text `#202b38`, secondary `#53616f`, accent `#515fb3`. Остальные значения светлой темы и ошибки показаны в `proposal.css` как проект, не как извлеченный светлый Sites 01.

Системная тема по умолчанию; явный выбор хранится на устройстве, доступен до входа и не меняет данные формы. Устаревшее наблюдение, остановка, ошибка и Git-изменения имеют разные подписи и роли цвета.

Отступы: 4/8/12/16/24/32/40 px. Радиусы: 7 px для полей/кнопок, 8-10 px для карточек, 999 px только для статуса. Поле 42 px на настольном экране, цель касания 44 px. Иконки 16/18/20 px, одна толщина контура; исходный набор Sites - Lucide. При внедрении использовать совместимый набор/обертку Vue, сохраняя доступные имена. Инициалы стеков имеют устойчивые цвета, независимые от состояния.

Декоративная линия и граница, необходимая для распознавания поля, - разные токены. Не делать все линии контрастными и не делать все поля почти невидимыми ради точного цвета Sites. Контраст текста минимум 4.5:1, крупного текста 3:1; значимых границ/состояний управления - 3:1 в применимых случаях. Проверять фактические соседние цвета и состояния, не только набор hex-кодов.

Настольный каркас - шапка 65, список 236, источник 265 px при достаточном месте. До 800 px сохранить раскрываемый список приложения вместо копирования горизонтальной полосы Sites: поиск и длинные имена должны оставаться доступными. Источник переносить под сервисы. Diff допускает собственную прокрутку/переключение сторон; страница не должна прокручиваться по горизонтали. Проверять 390/768/1280/1440 px и текст 200%.

## Минимальная библиотека компонентов

Не строить универсальный UI-kit. Достаточно компонентов, повторяющихся в реальных сценариях.

| Компонент | Обязательные варианты и поведение |
| --- | --- |
| Button / IconButton | Основная, вторичная, опасная; hover, focus, disabled, busy; одинаковые интервалы значок/текст; роль ссылки при навигации |
| Field / Select | Label, hint, error, disabled, readonly; ошибка связана с полем; введенное сохраняется при возврате |
| StatusBadge | Работает, остановлен, ошибка, нет данных, есть изменения; текст обязателен |
| StackItem | Выбран/обычный, длинное имя, Git-изменения, offline-сервер; полный текст доступен без hover |
| PageHeader / Tabs | Один заголовок, одно главное действие, прямые файлы/журнал, редкие действия в меню |
| SourceCard | Git, локальный, неизвестный источник, стек без управления; правдивая свежесть, ветка/коммит |
| ServiceTable | Нормальное, пустое, загрузка, ошибка, неизвестное; образ и порт при наличии данных; журнал по правам |
| Notice / EmptyState | Причина, последствия, следующее действие; Git-изменения не авария контейнера |
| DiffFile / ResultChoice | Сервер/Git/свой итог, скрытый/бинарный/удаленный файл, устаревший предпросмотр, ошибка проверки |
| StabilitySummary | Uptime отдельно от доступности; отсутствие и давность наблюдений; подробности по раскрытию |

Для каждого компонента определить имя, назначение, состояния, адаптивность, доступность и данные. Галерея должна рендерить будущие общие Vue-компоненты; сегодняшняя HTML-галерея является спецификацией на согласование.

## Этапы и точки приемки

- [x] S0. Получить исходный эталон, локальные ресурсы и происхождение; создать независимое превью.
- [x] S1. Подготовить предложение по шрифтам, темам, геометрии, компонентам и сравнению с текущим интерфейсом.
- [ ] S2. Пользователь утверждает этот дизайн-план и явные отличия от Sites. До этого не менять приложение.
- [ ] S3. После утверждения внедрить токены и общие примитивы в отдельной галерее настоящих компонентов. Проверить обычное, focus, busy, error и disabled в двух темах; выбрать итоговые значения контраста по реальным сочетаниям.
- [ ] S4. Собрать три основных сценария на общей системе: обзор -> создание -> Git. После каждого сравнить пару снимков. Учитывать Compose/docker run/отчет/возврат команды/save-only/выбор сервера, секреты и роли. Не переписывать сохранение Compose и авторизацию ради внешнего вида.
- [ ] S5. Довести дополнительные состояния: вход и переподключение без скачков, пустые и длинные списки, стабильность, настройки пользователей/MCP, наблюдатель. Существующий MCP остается в настройках, без новой постоянной панели.
- [ ] S6. Финальная приемка: реальные проверки поведения, lint, TypeScript, сборка, затронутые тесты; отдельно парные снимки и список оставшихся отличий. Обновить `docs/design-system.md` и карту функционального покрытия по факту.

Старые R1-R6 из аудита становятся задачами этапов S3-S6. Они не должны выполняться в обход S2. Новая точка согласования задана пользователем в запросе 13 сентября, а не придумана инструментом.

## Саморевью

Проверено после подготовки плана:

- Эталон отделен от улучшений. Нельзя обновить картинку эталона вслед за реализацией и объявить совпадение.
- Семейства уже совпадают: план исправляет шкалу и применение, не маскирует проблему новым шрифтом.
- Не строим дизайн-систему в отрыве от продукта: минимальный набор проверяется на обзоре, создании и Git.
- Противоречие "приглушить поля"/"сохранить доступность" разрешено разными ролями линий и проверкой контраста, а не слепым копированием слабой рамки Sites.
- Эталон не доказывает полноту функций. Сохранены docker run, роли, MCP, uptime, темы, исходные байты Compose и различие записи/развертывания.
- На стадии экспорта допускается замороженный пакет исходных зависимостей. На стадии внедрения второй React/Tailwind-интерфейс и дублирование токенов не допускаются.
- Визуальные сравнения не доказывают работу Docker, безопасность ролей или отсутствие сдвига после входа. Эти проверки остаются отдельными.
- План еще не утвержден пользователем. S2 остается открытым.
