# Dockge2: состояние и три направления интерфейса

Дата: 2026-09-07. Проверенная ревизия приложения: `edf3fe9`. В начале работы незакоммиченных изменений не было. Это исследование и макеты; новый интерфейс в Vue-приложение не внедрен.

Дополнение от 2026-09-08: функциональная сверка в `docs/design/2026-09-08-functional-coverage.md` выявила пропуски в трех макетах, включая docker run, сохранение без запуска и обновление образов. Макеты показывают направления дизайна, но не покрывают весь существующий функционал.

## Как проверено

Изучены исходники frontend, backend, общие функции, тесты, конфигурация CI и история последних изменений. Текущий интерфейс открыт в браузере на временной базе и трех демонстрационных Compose-файлах. Сторонние стеки, обнаруженные через Docker, только отображались; команды управления ими не запускались.

Исходный Dockge сравнивался по официальному репозиторию и изображению интерфейса из README:

- https://github.com/louislam/dockge
- https://github.com/louislam/dockge/assets/1336778/26a583e1-ecb1-4a8d-aedf-76157d714ad7

## Что уже есть

| Возможность | Подтверждение |
| --- | --- |
| Создание из Compose и преобразование docker run | `frontend/src/components/CreateStackSheet.vue` |
| Страница стека, команды, сервисы, доступность | `frontend/src/pages/StackInspector.vue` |
| Выбор файлов и отдельные настройки панели | `backend/stack-config.ts`, `frontend/src/components/StackFilesEditor.vue` |
| Сохранение исходного текста Compose | `common/compose-editor.ts`, `backend/stack.ts`, тесты сохранности |
| Происхождение Git, ветка, локальные правки | `backend/stack-source.ts` |
| Предварительный просмотр обновления образов | `StackInspector.vue`, `docker-socket-handler.ts`, `backend/image-updates.ts` |

Чтение Git ограничено локальным состоянием: `behind` вычисляется относительно последнего известного upstream, без `fetch`. Метод `Stack.update()` выполняет `docker compose pull` и `up`, а не получение исходников из Git. Законченного сценария clone/fetch/diff/разрешения конфликтов в текущем коде не найдено.

Факт наличия защиты Compose подтвержден реализацией и тестами. Нельзя описывать всю защиту от перезаписи как отсутствующую или обещать, что абсолютно любой путь уже проверен.

## Что мешает простоте

1. Главная страница постоянно показывает большую форму создания нового стека, даже когда человек пришел обслужить существующий. Форма использует основную рабочую область.
2. Compose-файл в инспекторе находится в меню дополнительных действий. В исходном Dockge связь между контейнерами, файлом и журналом видна непосредственно.
3. Пустая панель терминала остается внизу и расходует высоту экрана.
4. В шапке, полосе внимания и списке повторяются сведения о состоянии. Метаданные мелкие и визуально близки по весу к действиям.
5. Состояние Git и состояние контейнеров недостаточно четко разделены. Кнопка обновления рядом с Git-сведениями может быть понята как обновление репозитория, хотя выполняется загрузка образов.
6. Старые документы расходятся с кодом: в AGENTS.md отсутствовали реальные тесты и пороги покрытия; `docs/design-system.md` содержит и описание предпросмотра обновления, и запись о нем как о еще не выполненной работе.

## Три макета

Общая демонстрация: https://design-preview.example.invalid

Sites подтвердил успешное размещение с доступом только для владельца 2026-09-07. Все три варианта доступны по одной ссылке.

Макеты находятся вне исходников приложения: рабочая копия демонстрации лежит
в локальном каталоге визуализаций автора и в репозиторий не входит.

| Вариант | Компоновка | Сильная сторона | Ограничение |
| --- | --- | --- | --- |
| 01. Знакомый Dockge | Список слева, стек справа, прямые вкладки файлов и журнала | Простой переход от исходного Dockge; быстрое переключение стеков | Боковой список постоянно использует часть ширины |
| 02. Спокойный обзор | Светлый экран с карточками приложений и выбранным стеком ниже | Быстро узнавать приложения и видеть состояние небольшого сервера | Карточки расходуют больше места при большом числе стеков |
| 03. Файлы в центре | Список стеков, дерево файлов, Compose и сервисы под ним | Файл и Git доступны при частых изменениях конфигурации | Больше деталей одновременно; ближе к редактору |

Рекомендация: вариант 01. Он сохраняет знакомую модель исходного Dockge и добавляет Git как отдельное действие в контексте стека. Вариант 02 подходит для нескольких приложений; вариант 03 разумен, когда редактирование файлов происходит чаще, чем проверка состояния.

## Общий сценарий сравнения

Демонстрационный стек paperless продолжает работать. На сервере образ 2.14 и порт 8010; в предлагаемой версии Git образ 2.15 и порт 8000. Сравнение показывает `compose.yaml`, `.env.example` и `README.md`.

Можно оставить локальный файл, взять файл из Git или изменить итоговое объединение. Пока выбор для Compose не сделан, переход к итоговой проверке недоступен. После выбора показываются результаты по всем файлам и последствия применения. Сохраненная локальная версия продолжает считаться отличием от Git.

Сценарий создания: адрес репозитория/вставка Compose -> ветка и сервер -> имя стека и Compose-файл -> демонстрационный запуск. Есть проверка формата имени, переключение стеков, вкладки файлов и журнала, поиск и сброс сценария.

Это интерактивные демонстрации на вымышленных данных. Они не клонируют Git, не проверяют конфигурацию через Docker и не запускают контейнеры. Переходы показывают целевой пользовательский сценарий, а не подтверждают наличие этих функций в приложении.

## Проверки

- Приложение: `npm run lint`, `npm run check-ts`, `npm run build:frontend`, `npm test` успешно.
- Тесты приложения: 190 пройдено, 0 ошибок. Покрытие строк/выражений 81,85%, ветвей 85,47%, функций 85,2%.
- Полные Docker-интеграционные и E2E-наборы в этой задаче не запускались: код приложения не менялся.
- Макеты: проверены переключение трех направлений, выбор локального файла, разблокировка итогового шага, итог применения с сохраненными отличиями, создание и отклонение некорректного имени.
- Проверены настольное отображение и узкий экран; сравнение на узком экране показывает версии последовательно. Длинные имена образов переносятся, чтобы измененный тег был виден.
- Исходники демонстрации проходят отдельные lint/TypeScript-проверки и статическую сборку. Общий lint автоматически созданного набора компонентов Sites обнаруживает замечания в поставляемых компонентах; они не выдаются за исправленные. Используемый пользовательский код проверен отдельно.
- Вспомогательный WebMCP-переход между макетами проверен на допустимом и недопустимом вводе.
