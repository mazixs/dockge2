# Dockge2 design system

This document describes the current implementation of the "Familiar Dockge" direction: the value layer (the scale of type sizes and line heights, weights, spacing, sizes, radii, motion and layers) and the layout of the screens. The values come from `frontend/src/styles/tokens.scss`; contrast and consistency are checked by `test/frontend/design-tokens.test.ts`; the reference look is the screenshots in `test/visual/baseline/`, which `npm run test:visual` compares against.

## Purpose and layout

A simple Compose panel for the owner of a server and the users the owner has given access to. The first screen answers: what is running, what needs attention, and how to open or add a stack. Do not grow the panel into general infrastructure administration.

- A header 65 px high: the mark, the server picker, the connection state and the account menu. The menu is built in groups: working with stacks, the settings sections, and at the bottom the theme picker and sign-out. The theme picker is an ordinary form control (`ThemePicker`): in the settings it takes the width of a field next to the language picker, and in the header and before sign-in the same control is shown compact. The server picker filters the list and the global overview; adding an agent is available to the owner in the settings.
- On the left, 236 px wide: the global overview, search, collapsible filters and the list of stacks with their states in words. Adding a stack has its own button, on the phone as well.
- Search and filter live in the address (`?q=`, `?filter=`), and the links inside the list keep them: a narrowed list survives opening a stack and a reload. A server group shows 50 rows, then a dashed "Show N more" button at the end of the group; the open row is always visible. Compose projects outside the stacks directory and containers outside any project are folded into groups of their own with a quiet row style; a container opens its own page, not a stack page.
- The global overview starts with what broke: above the state counts stands the attention strip, which names the stacks with their reasons and leads to the filtered list. The counts count containers and the strip counts stacks, so it answers "which ones exactly" rather than repeating the number.
- Sign-in and the first run are a card in the middle of the area under the header, without the stack rail: the person has not said who they are yet, and there is no reason to show them what belongs to others.
- On the right: the current page. The home page shows container stability; a selected stack shows its services, actions, availability and source.
- "Overview", "Files", "Logs" and "Terminal" are tabs of one stack page, not separate screens. Each has its own address, but the stack header, the side list and the page stay in place: only the work area changes. The arriving panel is marked by motion, and the leaving one is removed at once so that the page does not jump.
- The work area of every tab is built the same way: a main column and the 265 px source panel on the right. On the overview the main column holds the services and availability, on the files tab the editors, in the logs and the terminal the console; the source stays in place, so switching tabs does not rebuild the page.
- The logs and the terminal are separate. The logs tab shows the output of the stack and nothing else: one console, nothing to choose, no input accepted, and the note under the console says so. The terminal holds container shells: tabs of the open sessions with a close button, "Open shell" with a list of the running services - the same words as in the service menu - and a note that commands run inside the container.
- Every panel of the work area has one anatomy (`.panel` in `main.scss`): a hairline border, the panel radius, no shadow; a header as high as a control plus padding, holding an outline icon of the object's kind, the name (a file name in monospace), a quiet label at the right edge ("On server", "Git", a count) and actions at `btn-sm` size; the body; a note in small type under a line, where a green shield means only one thing - the promise that the source text is kept. There are no headings between panels: the panel header gives its name. Panels do not nest: a list inside a panel is rows under hairlines (services, secret files). Delete in a row is an ordinary button with a red word, not a red fill. Lists inside a panel are built from `.panel-rows` / `.panel-row`, a text editor from `.editor-box`, a console from `.panel-console`. The space between an icon and its label comes from the button itself: the `me-1`, `me-2`, `ms-1` and `ms-2` utilities on a button's direct children are cancelled, or the spacing would drift from screen to screen.
- The headers of all panels have one height and stand on one line with the header of the source panel on the right, so the eye does not have to readjust when the tab changes. The logs and a terminal with an open shell grow to the bottom of the page: the console shows as much as the screen holds. The console surface keeps its text inset from the border, and xterm gets its colours from tokens - background, text, cursor and selection: with its own theme it paints pure black, and in the light theme a black rectangle inside an almost black panel left a visible seam. An empty terminal does not show a black rectangle: it shows a choice of service instead, and the console appears with the first shell. There is no bottom panel. Sessions survive switching to another tab of the same stack and do not carry over to another stack.
- The progress of a command is one line under the stack header, above the tabs: it is visible from any tab and takes the height of a line, not of a panel. It holds the outcome mark, the command in a word ("Starting", "Restarting", "Updating"), what is happening right now ("Container paperless-web starting"), the step count, the seconds, "Stop", "Show the output" and a close button. Along the bottom edge a thin thread shows compose's own count; without a count it runs by itself.
- A service state is not duplicated: while a command runs, the "State" column of the services table uses compose's words ("creating", "starting", "started"), the dot of the chip breathes, and a few seconds after the end the word comes from the Docker measurement again. The progress line says only what the table does not: networks, volumes, image pulls, the total time and aborting.
- After success the line leaves by itself; after a failure it stays, turns red and names the step that failed. The black window is not forced on anyone: the full `docker compose` output opens with the "Show the output" button in a window over the page - the steps on top (outcome mark, kind icon, name, what is happening, how long it took) and the console below. The output of the last command can always be reopened from the stack's "More" menu ("Last command output").
- The stack tab strip does not break the page: when it does not fit, it scrolls by itself, and below 480 px the tab icons go - the tab name matters more than the icon.
- Below 800 px the list opens with a button above the work area. After a stack is chosen the list closes and focus moves into the work area. Tables scroll inside their own area. The source panel moves under the services, already below 1250 px. The settings have a way back to the list of sections. The drawer does not repeat the section name - it is already on the button that opened it. The file strip of the comparison and the service tags of a secret go onto new lines instead of being cut off by the edge of the screen, and the two ways of creating a stack share the width of one segmented switch.

## Themes and colour

The first visit follows `prefers-color-scheme`. The light, dark and system themes are available before sign-in. An explicit choice is stored in the browser; a change of the system theme and a choice made in another tab apply without a reload.

Components use the shared tokens. The light values are set on `:root`, the dark ones on `body.dark`; the values in `vars.scss` match them for the existing Bootstrap components.

| Purpose | Token |
| --- | --- |
| Page, panel, side list | `--surface-base`, `--surface-panel`, `--surface-sidebar` |
| Raised and sunken surface, selection | `--surface-raised`, `--surface-sunken`, `--accent-soft` |
| Primary and secondary text | `--text-strong`, `--text-muted`, `--text-faint` |
| Main action and its label | `--accent`, `--text-on-accent` |
| Link | `--accent-text` |
| Divider and field border | `--line-hair`, `--line-control` |
| Console, text and selection on it | `--surface-console`, `--text-on-console`, `--surface-console-selection` |
| States | `--state-running`, `--state-attention`, `--state-stopped`, `--state-unknown`, `--state-failed`, `--state-changes` |

The dark theme accent is `#9dacf9`, the background `#111419`, the panel `#191d24`. The light theme uses `#515fb3` for interactive elements. Green means that a service is working; a state always has a label. Text and state colours need a contrast of at least 4.5:1 on every surface of the system, and field borders 3:1 against the page background. The console and the code editors use a separate dark surface with matching syntax highlighting in both themes. A muted state (for example a zero counter on the home page) takes its own `--state-*-quiet` colour rather than `opacity`: contrast is computed on the resulting colour, and `test/frontend/design-tokens.test.ts` checks these tokens the same way as the main ones.

## Scale, density and motion

Colour was described with tokens before the other dimensions, so type sizes, line heights, weights, layers and durations lived as numbers inside components. Now these dimensions are set in `tokens.scss` too, and `test/frontend/design-tokens.test.ts` forbids a number for `font-size`, `line-height`, `font-weight` and `z-index` in a component.

| Purpose | Tokens |
| --- | --- |
| Type size | `--text-xs` 12, `--text-sm` 14, `--text-base` / `--text-md` 16, `--text-lg` 22, `--text-title-sm` 26, `--text-xl` 30, `--text-code` 13 |
| Line height | `--line-xs` 18, `--line-sm` 20, `--line-base` / `--line-md` 24, `--line-lg` 30, `--line-title-sm` 32, `--line-xl` 36, `--line-code` 21 |
| Weight and tracking | `--weight-regular` 400, `--weight-medium` 500, `--weight-strong` 600, `--tracking-title`, `--tracking-eyebrow` |
| Spacing | `--gap-xs` 4, `--gap-sm` 8, `--gap-md` 12, `--gap-lg` 20, `--gap-xl` 24, `--gap-2xl` 32, `--gap-3xl` 40 |
| Sizes | `--control-height` 32, `--control-height-sm` 24, `--control-height-touch` 44, `--field-height` 42, `--row-height` 40, `--row-height-dense` 34, `--icon-sm/md/lg` 16/18/20 |
| Radii | `--radius-chip` 3, `--radius-control` 5, `--radius-panel` 7, `--radius-card` 10, `--radius-pill` |
| Motion | `--motion-fast` 100ms, `--motion-base` 160ms, `--motion-slow` 240ms, `--motion-ease`, `--motion-ease-in` |
| Layers | `--layer-sticky`, `--layer-header`, `--layer-dock`, `--layer-modal`, `--layer-toast` |

Every type size has its own line height. One size is not enough: at different line heights the same 14 px give a different density of lines, and density was exactly where the implementation differed from the reference. There are three weights and no synthetic bold. Under `prefers-reduced-motion` the durations are set to zero in the token file itself, not in each component. On a narrow screen (below 900 px) the scale is swapped in the same place: the tap target and the field grow to 44 px, and `--gap-3xl` shrinks to `--gap-lg`.

Two deviations from the proposed system 0.1 are deliberate. The 20 px spacing step is kept because it is already built into the layout of the header and the list. `--state-changes` is a role of its own: Git edits are not a container failure and must not share a colour with `--state-attention`.

## Typography and controls

Local IBM Plex Sans for the interface and IBM Plex Mono for files, paths, images and command output. Sizes, radii and spacing are set by tokens: body text 16 px, labels 14 px, page titles 30 px. The colour of a stack's initial depends stably on its first letter; the state is given by a separate label. At the bottom of the list are "New stack" and a shield with the caption "Your server. Your files.". The minimum tap target is 32 px on desktop and 44 px on a narrow screen.

- Buttons name the action. The header holds start or stop, and restart for a running stack. Checking for image updates is available through the menu.
- A state is shown by one chip at every level (`StateChip`): a dot in the state colour, the word next to it, and an icon when attention is needed. There is one vocabulary: a stack, a service and a container name the same thing in the same words, without abbreviations. The chip label starts with a capital letter, and the rule lives in the chip itself, not in the catalogue: the same words in the progress line stand inside a sentence and get no capital there.
- A disabled button looks the same for every variant: no variant fill, only a thin border and a muted label from the tokens. An unavailable action has no weight, and a variant fill would promise the opposite. Bootstrap's opacity is cancelled, or the contrast of the label would depend on whatever happened to be under the button.
- Attention is drawn as one box (`.attention-block`) with a badge at the left edge (`.attention-badge`). On the global overview the badge names the state ("Attention") and the stack names with their reasons stand next to it; on a stack page it says "Reason", followed by what fixes it. The screen sets the layout and the system sets the look: while the look was written out in two components, the badges drifted apart in letter case.
- Dangerous actions are placed in the menu. Delete warns that the stack directory and any data inside it will be removed; `down` ("Stop and remove containers") needs its own confirmation.
- Outline icons of the main transitions use `InterfaceIcon`. Filters are buttons with `aria-pressed`; navigation is links with a current state. Interactive icons have an accessible name.
- Tables have a `caption`, `scope` and row headers. Service actions are available without hovering. A row menu pops up over the table and does not push it apart; its items are labelled with the action, not with an icon alone, and the menu closes after a choice.
- An open terminal session gets focus at once: otherwise the first word goes into the button that opened the session.
- Truncation with an ellipsis is allowed, but it must reveal what is hidden: the `v-ellipsis-title` directive sets a tooltip exactly when the line does not fit and removes it when there is room again. A tooltip that repeats the visible text is noise. Where the width of the text cannot be measured (the server picker is a `select`), the tooltip is always there. Screen reader users get the full name from `aria-label`, not from the tooltip.
- The console waits for its font: the character cell is measured once, and a measurement taken with the fallback monospace font would leave the grid mismatched with the width of the panel until the first window resize.
- Focus is visible. Transitions respect `prefers-reduced-motion`. Colour and a hover tooltip do not replace a state in text.

## Creation and files

The `/new` page opens from the "New stack" button, from pasting text outside a field or from dropping a file. The Git tab ("From Git") asks for the address, the branch, the server, the name and the Compose file. The Compose tab ("Paste Compose") uses the built-in form `CreateStackSheet.vue`; it accepts Compose and `docker run` / `sudo docker run`.

The conversion keeps the original command so that it can be brought back, and shows a report on the parameters: what was carried over, what needs checking and what is not supported. The absence of a converter error does not prove that every flag was carried over. Choosing the agent, the stack name and saving without starting remain part of the scenario.

Every file is a panel of the shared anatomy: the file name in the header, the "On server" label, copy and the editor actions, the text inside, and under it a note that this is the source text with its comments ("Source text, comments included"). Compose and the active env file are two such panels, and both are visible in read mode: edit mode decides whether the text can be changed, not whether the file is on the screen. The "Edit" button stands in the header of each panel and switches on one shared edit mode. It is accented only on Compose, because the screen has one main action; on the env file the same button is an outline one. Saving and deploying stay one set in the Compose header. An empty env file says so in a line of text, not with an empty console surface. Below them, in the same anatomy, stand "File selection" (Compose, the env files, the interpolation order, creating a new env file; the save button in the header) and "Secrets" (each file is a row with tags for its name and services; services are chosen with checkboxes, like the env files). In edit mode the containers are rows of one list in the "Containers" panel, and the settings of a service open under its row. Untouched source text is saved without rebuilding the YAML. Reading, starting and updating images are not permission to write Compose. Panel metadata is kept separately. Creating a file, including it in interpolation and opening it in the editor are three separate steps: a single action would change the text under an open editor. While the file selection is not saved, the creation form is closed and says so.

## Source and updates

The source panel shows the local directory or what is known from Git: the remote address without credentials, the branch, local edits and how far the branch is behind the last known upstream branch. This is a local read, with no network `fetch`.

"Update images" runs the existing preview flow and `docker compose pull`, then `up` if the state of the stack calls for it. This button does not fetch the sources from Git.

The Git button of the source panel - "Check for updates", or "Compare changes" when changes are already known - fetches the current Git branch and opens the "What changed" page. The page shows the current and the target commit, the list of files, the "On server" / "From Git" versions and line highlighting. Every changed file needs an explicit choice; then the result is validated and saved, with or without starting. Secret files are hidden, and the content of binary files is not shown.

Saved local versions remain differences from Git. For ordinary text files "Edit result" is available right in the comparison, before writing. Hidden and binary files are not edited in this view; the existing editor stays a separate flow. Fast-forward and Compose/env files at the root are supported; the limits and recovery are described in `AGENTS.md`. After a server restart or after 10 minutes the comparison has to be fetched again.

## Stability and uptime

The global overview groups the real containers by stack and agent; containers without Compose are shown separately. For each container the state, health, time since start, restart count and history over 24 hours, 7 or 30 days are available.

One server is one table: the columns are named once and stand on a shared grid, and a stack becomes a shelf inside it (a `<tbody>` with a header row on its own background). Separate tables for each stack broke this grid: the headers repeated and the columns did not line up between stacks. The stack name on a shelf is written as in the list on the left - without an underline, which appears on hover and focus.

- Uptime is the time between Docker's `StartedAt` and the moment of the last observation. After a stop, or when the data is stale, the current uptime is not shown.
- Availability is the share of confirmed time in a working state. It is not an HTTP check of the service. The percentage appears after a minimum observation period; the coverage of the window is always shown next to it.
- The server collects observations at most once a minute, whatever the number of open pages. After 90 seconds without a fresh observation the current state is unknown.
- Gaps in observation do not extend the previous successful status. History saved under the old scheme stays in the database, but unconfirmed intervals do not become a retrospective 100%.
- The coloured history has a legend, a text description and details of the intervals. When Docker or an agent is unavailable, the reason and a retry are shown, and the old current figures are hidden.

## Accounts

There is no public sign-up. The first owner proves ownership of the instance with a one-use code; further accounts are created by the owner in the settings. Deployment and recovery details are in `docs/authentication.md`.

The owner manages accounts and settings. An operator manages stacks and Docker and is a trusted user of the host. A viewer sees statuses without the content of files, secrets, logs and the terminal. Hidden interface elements only reflect the server-side permission check; they do not replace it.

## Checking changes

For an application change: lint, TypeScript, the relevant tests and a build. Check transitions on desktop and on a narrow screen, the three theme modes, and the loading and error states. For permissions, check forbidden server operations and the revocation of active sessions; for stability, gaps, stale observations, containers without a healthcheck and an empty Docker.

Checks run with separate database and stack directories. Other people's containers can appear in the Docker list even with this isolation; they must not be controlled while the interface is being checked.

The look of the screens is pinned by reference screenshots: `npm run test:visual` compares fourteen screens in the light and dark themes at 1280 px and six of them on a 390 px phone. The screenshots are taken from a test scene with frozen time, so a difference means a change to markup, tokens or fonts, not noise from the environment. The references live in `test/visual/baseline/` and are committed.

The reference is re-approved with a separate command, `npm run test:visual:approve`, and only when the look was changed on purpose. A screenshot that is updated along with every edit stops being a reference and catches nothing.

## Review of 15 September

The second pass of the same day went through a live instance and closed differences that are visible only side by side. The state vocabulary was reduced to one: the abbreviations the Russian catalogue gave for "active", "exited" and "inactive" were removed together with the helper that produced them, the chip now capitalises the first letter of its label itself, and a stack, a service and a container name a state in the same words. Before this, one screen showed "Error" in the header next to the abbreviated "exited" in the services table. The attention strip returned to the global overview: it existed in the code, but after the home page was rebuilt it stood on no screen. Its look and the look of the reason block on the stack page became one system box. A disabled button got one inactive look instead of the fill of its variant. The panel header stopped depending on the heading level (`h2` gave 22 px where 14 stood next to it). The settings column is limited to 720 px. After a failed read the MCP section shows the reason and a retry, not a form of default values that a save would have written over the settings. A zero in the state counts is muted: an orange "0 Needs attention" read as a warning. A file whose name the name allow-list rejects no longer disappears from the screen - it is named in a separate block with the reason and a way to fix it.

The third pass of the same day went not through the scene but through a live instance with its own stacks, and closed what is visible only there. A page made of one console - the server console and a container shell - fills the work area to the bottom: a height set as a number of rows left an empty quarter of the screen under the panel, and half of it on a tall monitor. The console header names the server rather than repeating the page name: a console can also be on an agent, and the word "Console" twice in a row adds nothing. The delete button of the last active owner is disabled, and the panel note says why: the server would refuse, and a button that always ends in an error promises an action that does not exist. The MCP section tells a denied access apart from a failed read and does not offer a retry where a retry would return the same answer word for word.

The checkbox became shared anatomy in `main.scss`. Bootstrap floats the box with a negative left margin, and in a row it slid past the left edge of the panel, where the border cut it off. The rule was written out as copies on three screens, and on one of them it lost to Bootstrap by load order rather than by selector weight, so it now lives in the shared stylesheet after the Bootstrap import, where it wins deterministically. The editor box keeps room for six lines: on a short or empty file it shrank to one, and the surface stopped reading as a place to write in. The product name became one component, `BrandMark`. Before that it was written differently in the header, on the first run and in the about section, sometimes "dockge2", sometimes "Dockge", and sign-in had no mark at all, although the design system promised one. Small things from the same pass: the count in a panel header is separated from the neighbouring button by a larger step, or it read as that button's label, and the server name in a row of the agent list capitalises its first letter with the same `::first-letter` rule as the state chip - in the stack header the same name stands inside a sentence and must not be capitalised there.

The fourth pass looked at the same things from a phone and at the places where an element marks itself. The rail marks the open stack on all its tabs, not only on the overview: the tab routes are siblings of the overview, not its children, so `router-link` considered the item active on only one of five pages. A long name in the rail gives a tooltip on hover, and only when it really is truncated - the same rule as for the progress line and the facts line on the stack page. The header of the services table moved out of the `caption` and now stands above the scroll area: on a phone the table is wider than the screen, and the service count, the check time and the column menu - everything used to control the table - scrolled off to the right with it. On a narrow screen the attention strip puts its action on a line of its own and keeps the badge and the reasons on the first: in three columns the reason got ten characters of width and broke mid-word. The stack drawer on the phone stopped being a second scroll area inside a third: only the list scrolls, and the create-stack button is visible under it.

Tap targets were brought into the system. The tokens gained `--control-height-sm` for a small control in a block header, and on a narrow screen it grows to the same value as an ordinary control - the availability window picker was 24 px and could not be tapped with a finger. The external network switch is drawn at the same 34 x 20, but its tap target now takes the full height of a control. The current item of a dropdown menu is marked with the soft accent, like a row in the rail, and with the accent word, like a settings section: a solid fill read as a mouse selection, not as "you are here". In the stack menu every item has an icon - without one, the label of the first item stood further left than the rest. An MCP section that could not be read is explained by the same box as the disabled console: the title names the state and the hint names the reason. The panel for turning off sign-in is named after what is done in it ("Signing in"), not with the word "Advanced".

The fifth pass went by keyboard and by contrast figures. The output terminal no longer takes focus when it opens and no longer swallows Tab: the logs tab opened with the cursor inside the console, and there was no way out by keyboard - neither to the stack tabs nor to the close button of the run window. Arriving in the console and in the editor is now visible: the ring is drawn by the box around them, because the input field of xterm is hidden and one pixel in size, and the xterm canvases lie above the outline and covered it completely. The Tab order was walked on all fourteen routes: from 24 to 41 stops, and none without a visible mark.

State was recognised as text. Green, orange, grey and red appear not only as a dot and a fill but also as a word - next to the container counter, in the stability verdict, in the Git edit line - so they carry the same threshold as text: 4.5 on every surface of the system, not 3 on two. The four states and the muted text were shifted by a few units of lightness, which the eye does not notice, and the test now checks all five surfaces - base, panel, rail, raised and sunken - for both token lists. The panel title became a heading everywhere. Now each of the fifteen screens has exactly one `h1` and no skipped level.

The reference was extended. The scene gained a stack that needs attention (without it neither the chip of that state nor the strip made it into the screenshots), and sign-in is captured as it looks in the application - without the stack rail the scene used to give it.
